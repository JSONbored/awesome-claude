## Safety Notes
- Migration debugging may run package manager scripts, tests, builds, generators, and git commands; review scripts before executing unfamiliar project code.
- Avoid broad dependency upgrades, generated artifact churn, or formatting sweeps unless the migration explicitly requires them.
- Create rollback points before destructive commands, data migrations, lockfile rewrites, or cross-package refactors.

Use local repository evidence first, then official migration guides, changelogs, and installed package metadata.

## Core Workflow
1. Establish a baseline: git status, runtime versions, failing command, shortest reproduction, and known-good reference if available.
2. Map affected files, packages, configs, generated outputs, and tests before editing.
3. Identify the smallest change that explains the failure and defer unrelated cleanup.
4. Apply fixes in rollback-safe increments with validation after each risky boundary.
5. End with a validation ladder from narrow reproduction to broader build/test checks.

## Capability Scope
- Dependency and runtime migrations
- Build, type-check, lint, and test failure diagnosis
- Monorepo package boundary debugging
- Partially applied refactor recovery
- Rollback-safe validation planning

## Compatibility

- **Claude Code IDE surfaces**: use when editor diagnostics and selected context are useful.

### Manual Adaptation

- **Codex, Cursor, Windsurf, Gemini, and similar agents**: use the workflow as a repo migration/debugging checklist.

## Production Rules
- Reproduce before changing unless reproduction is impossible; if impossible, state why.
- Prefer narrow, causal fixes over broad rewrites.
- Keep lockfile and generated artifact changes intentional.
- Validate the exact failing path before claiming the migration is complete.

## Troubleshooting
**Issue:** The failure changes after the first fix
**Fix:** record the original failure, new failure, and boundary crossed; do not conflate them.

**Issue:** A migration guide suggests many changes
**Fix:** split required compatibility changes from optional modernization and implement only what the issue requires.

**Issue:** Tests are unavailable or too expensive
**Fix:** run syntax/type/build checks where possible and provide a precise manual verification path.

## Output Contract
1. Reproduction summary and root-cause hypothesis.
2. Minimal patch plan with rollback points.
3. Applied changes grouped by cause.
4. Validation ladder with commands and results.
5. Remaining risks, skipped checks, and follow-up work.
