## TL;DR

Open-source repositories should treat AI coding agents as powerful contributors,
not as trusted maintainers. Agents can edit code, trigger CI, suggest dependency
updates, and create convincing pull request summaries, but the repository still
needs least-privilege permissions, scanner evidence, and human merge ownership.

The goal is not to ban agents. The goal is to make the workflow boring: every
agent-created branch goes through the same protected path as any other untrusted
change.

## Core Concepts Explained

### Agent branches are untrusted input

An AI coding agent may run commands, edit files, update lockfiles, and summarize
its own work. That does not make the branch trustworthy. Review the final diff
as untrusted input and verify the behavior through CI, tests, and human review.

### CI is a security boundary

CI jobs often hold repository tokens, cloud credentials, package-publishing
permissions, and access to private caches or artifacts. A generated workflow
change can be more dangerous than an application-code change because it may
alter who can execute privileged automation.

### Human approval should stay in the merge path

Agents are useful for implementation and triage, but the merge decision should
belong to maintainers. A protected branch or ruleset gives the project a
repeatable place to enforce that decision.

## Step-by-Step Implementation Guide

1. **Create an agent access policy.** Write down which agents may open pull
   requests, which repositories they may access, whether they can run commands,
   and whether they can read secrets. Keep production deployment, release, and
   package-publishing permissions outside the default agent role.

2. **Scope `GITHUB_TOKEN` permissions.** Configure repository and workflow
   permissions so jobs receive only the access they need. Prefer read-only
   defaults, then grant write scopes explicitly for narrow workflows that require
   them.

3. **Treat forked PRs carefully.** Pull requests from forks are part of normal
   open-source collaboration, but they are also untrusted. Do not expose secrets
   or privileged write paths to unreviewed fork code. Be especially cautious
   around workflows that run with elevated context.

4. **Protect the default branch with rulesets.** Require reviews, status checks,
   linear history or merge rules as appropriate, and block direct pushes from
   agent accounts. Put the same rules around files that control CI, releases,
   package publishing, deployment, and repository policy.

5. **Add scanner gates.** Run secret scanning and dependency review before merge.
   Add code scanning or a local equivalent for application changes. A scanner
   result is not a substitute for review, but it gives maintainers concrete
   evidence to inspect.

6. **Review workflow and dependency diffs first.** If the agent touched
   `.github/workflows`, package manifests, lockfiles, install scripts,
   containerfiles, or release automation, inspect those files before reviewing
   ordinary application code.

7. **Require reproducible verification.** Ask the agent operator or contributor
   to list the exact test commands, generated files, and manual checks used.
   Merge only when a maintainer can reproduce or independently inspect the
   evidence.

8. **Keep logs and artifacts on a short leash.** CI logs and artifacts may hold
   prompts, file paths, environment names, generated code, or accidental secrets.
   Set retention deliberately and avoid uploading broad workspaces as artifacts.

9. **Review the agent account itself.** Use a dedicated bot or service account
   where possible, with auditable access and no personal long-lived credentials.
   Rotate credentials after suspected exposure and remove access when the agent
   is no longer used.

## When to Block the Merge

Block or request changes when an agent-created PR:

- Grants broader workflow, repository, cloud, package, or deployment permissions.
- Changes `pull_request_target`, release, publishing, or deployment automation
  without a clear security rationale.
- Adds dependencies or install scripts without explaining why they are needed.
- Uploads broad workspace artifacts, logs secrets, or changes retention policies
  without review.
- Claims tests passed but does not provide reproducible commands or CI evidence.
- Includes a generated summary that does not match the actual file diff.

## Troubleshooting

- **The agent needs write access to update the branch**: give it the narrowest
  branch-specific permission possible and keep the default branch protected.
- **A workflow needs secrets for legitimate tests**: run the privileged job only
  after maintainer approval, or split untrusted tests from trusted deployment
  jobs.
- **Dependency review blocks a generated lockfile update**: ask for a smaller PR
  that isolates the dependency change and explains the upgrade path.
- **A scanner warning is accepted**: record the rationale in the pull request so
  future maintainers can audit the decision.
