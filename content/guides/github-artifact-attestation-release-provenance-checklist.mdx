## Why this matters

AI-assisted release work is only useful when the assistant can point to evidence
that a published artifact came from the expected repository, workflow, commit,
and build path. GitHub Artifact Attestations provide that evidence by binding an
artifact digest to provenance generated by GitHub Actions. This checklist keeps
Claude or another review agent from relying on a release note, filename, or
maintainer claim when a verifiable attestation should exist.

## Release checklist

1. Identify the artifact that will be published, including its exact filename,
   digest, release tag, workflow run, and commit SHA.
2. Confirm the build workflow requests the required permissions for generating
   an attestation and does not run untrusted fork code with write privileges.
3. Generate the attestation in the same trusted workflow that produces the
   release artifact.
4. Download the final artifact from the release, workflow run, or package
   channel that users will actually consume.
5. Verify the artifact with GitHub CLI using the expected repository owner and
   repository.
6. Compare the verification result against the release notes: repository,
   workflow, commit, ref, subject digest, and builder identity should match.
7. Keep the public release summary short: say what was verified and link the
   artifact, workflow run, and verification docs rather than pasting long logs.

## AI review prompt

Ask the assistant to produce a provenance section with four fields:

- Artifact: exact file or package name and digest.
- Builder: repository, workflow, run, commit SHA, and ref.
- Verification: command used, expected owner/repository, and pass/fail result.
- Caveat: what the attestation does not prove, such as runtime safety,
  dependency vulnerability status, or installation trust.

If any field is unknown, the assistant should mark the release as needing human
review rather than filling the gap from memory.

## Common failure modes

- Verifying a local rebuild instead of the artifact users download.
- Publishing a generated release note that says provenance exists without a
  verification command or result.
- Reusing a workflow name from a prior release when the current artifact was
  built by a different workflow.
- Treating an attested artifact as safe to execute without dependency, malware,
  and runtime review.
- Forgetting that provenance can expose repository, workflow, and release timing
  metadata that may be sensitive before publication.
