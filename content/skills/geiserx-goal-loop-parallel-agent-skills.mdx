# GeiserX Goal Loop and Parallel Agent Skills

A set of skills for Claude Code and Codex in the shared `SKILL.md` format.
`skills/` holds the Claude Code copies and `codex/skills/` the Codex ones. The
durable loops drive one repository toward a goal. The parallel skills split a
review, an investigation, a research question or a change across independent
agents, then check what they found before acting on it.

## Knowledge Freshness

The skills change with the repository. This entry was verified on

the documentation over this summary when they differ.

## Core Workflow

1. Clone the repository and link the skills you want into `~/.claude/skills`
   (Codex: from `codex/skills/` into `~/.agents/skills/`).
2. Optionally install the SessionStart and Stop hooks from `runtime/` and add
   them to `~/.claude/settings.json`, so `/sergio-loop` continues in the same
   session.
3. Open a fresh session in the target Git repository.
4. Run `/sergio-loop <goal>` for a goal you want driven to completion, or call a
   parallel skill for a single task: `/review-pr 42`, `/investigate <failure>`,
   `/research <question>`, `/implement <change>`.
5. Resume an unfinished loop with `/sergio-loop`, or reopen a finished one with
   `/sergio-loop --continue`.

## Capability Scope

- `/sergio-loop` runs a goal loop in one repository, one small slice at a time:
  inspect and plan, implement, verify, then a fresh review. Goals and evidence
  live in `docs/GOAL.md` and `docs/AUTOPILOT-WORKLOG.md`, human-only decisions
  in `docs/DEFERRED-QUESTIONS.md`, and resumable state in `.omc/sergio-loop/`.
  Defaults are `max_iterations=50`, `no_progress_limit=3` and `failure_limit=3`.
- `/refine-loop` makes small improvements that keep behavior the same, ranked
  by `ROI = Impact x Confidence / Effort`, one per round, each checked by a
  fresh read-only reviewer.
- `/docs-loop` audits documentation against the default branch as a dry run,
  with staged edits (`--apply`), or with one pull request per repository
  (`--apply --open-prs`). It never merges.
- `investigate` reproduces a failure and names a root cause only when the
  evidence holds. It edits code only when the request asks for a fix, and then
  adds a test that fails for the root cause first.
- `review-pr` reviews the exact head of a pull request, checks every finding
  against the code, fixes the valid ones within the PR's intent and has a
  separate reviewer check the fixes. It stops after three rounds and never
  merges.
- `review-code` audits a repository in bounded waves and publishes every
  verified finding ranked by severity.
- `research` answers from the code, its history and primary sources, with a
  claim, a source and a confidence level for each finding.
- `implement` makes the smallest complete change, gives each parallel writer
  its own files, then integrates and verifies the result.
- `kb-research` and `kb-review` answer and review from your team's own record
  (chat archives, call transcripts, tickets, wiki pages) through one adapter
  file, `references/knowledge-base.md`.

The parallel skills scale their panel to the task: alone on a trivial task,
2-3 agents on a modest one, 4-7 on a normal one and 8-12 or more on a broad or
risky one. Agents never spawn other agents.

## Production Rules

- A stored goal or an earlier approval is context, not permission. Merging,
  publishing, deploying, production changes and history rewrites need
  authorization in the current session.
- Review every change a loop or `implement` makes before keeping it; each
  accepted change must pass the repository's own checks.
- Use `/docs-loop` without `--apply` first; it only reads.
- `kb-review` posts nothing unless you approve the exact text.
- The Stop hook only continues the bound repository and session, for up to
  eight consecutive Stop events, and lets context, auth and rate-limit failures
  stop normally.
